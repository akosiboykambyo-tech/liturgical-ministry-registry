# RC3.2 — Phase 1.6 integration contract
Design source: docs/design/parish-renewal/phase-1.6 (original artifacts byte-for-byte preserved). Current preview baseline 92991e7; current production is independent. Brand guide v1.0 checked: retain EB Garamond/Inter, crimson/oxblood, warm white, five circular steps and central card. Restore institutional assets using existing logo component; do not invent artwork. Design extensions only for accessible controls and error handling.
Confirmed later policies: mobile SMS OTP parish, email OTP staff (both mock in TEST), two mock coordinator slots, no partial payments, 12-month document retention, rates/exemptions pending COWL and privacy pending review. Step 4 submits a proposal; Step 5 waits for Registry approval and COWL finance authorization, then shows authorized immutable references. No applicant quote locking before authorization.
Audit: existing rc3_demo has 48 synthetic assignments, 2 ministries per parish; rc3_demo_online_submit takes assignment IDs for one parish/ministry and one generated letter. Existing RC3 links one application to one payment request. Do not fan out independent writes in the browser; a failure would strand a partial parish submission. Do not conflate a consolidated bill with independent payments. New names, name corrections, omitted roster decisions and document coverage need durable review records, not just selected IDs. Build a parent submission + per-ministry child/revision contract; atomic submission and idempotency; review proposals before assessment; keep legacy RC3.1 route functional until migration and QA. Design parent quote/item allocation against existing RC2 ledger (one full settlement, no partials) before enabling payment. No live member/encryption adapter until security baseline acceptance.
This increment implements pure CSV import/export, canonical six ministries via shared constants, matching proposals using existing name similarity, explicit omissions, conservative review requests and integer-centavo estimates. It is not yet wired to a UI or database. Similarity matches never silently renew; exact same-name ambiguity goes to review. Do not pass other parishes into the matcher. Revalidation and cross-parish review occur server-side in future. No actual upload or personal data. Tests cover these invariants and lock the source artifacts by hash.
Next implementation gate: confirm atomic parent/child schema and itemized quote/settlement contract in isolated TEST, then wire original five-step presentation and review queue, private synthetic documents and correction workflow. Run full browser acceptance, old RC2 regression, security/authorization and deployment checks before switching routes. No production changes or schema changes in this increment.
